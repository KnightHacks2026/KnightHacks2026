# Dataset import handoff

`POST /api/datasets/import` accepts the shared `ImportDatasetRequest`. Runtime validation covers identifiers, cross-dataset ownership, all account/instrument/source/obligation/dependency references, duplicate source identities, integer financial units, reserved inventory, and dependency cycles. Invalid bodies return `VALIDATION_FAILED` with field-level `validationIssues`; a reused dataset ID returns `REVISION_CONFLICT`. The fixed `dataset-cascade` ID is reserved for the fixture.

The repository uses Node 24's built-in SQLite driver. It creates `data/custodyos.sqlite` on the first imported-dataset access, or the path in the trusted server configuration `CUSTODYOS_DATABASE_PATH`. Fixture-only reads do not open a database. The dataset payload, immutable revision `1` financial snapshot, and `DATASET_IMPORTED` audit event are committed in one SQLite transaction. SQL parameters protect dataset identifiers from injection. JSON retains the public contract's decimal strings. A second import does not replace a revision, since the v1 import request has no `expectedDatasetRevision`; future revision updates need a separate approved API contract and atomic write path.

Workspace, twin, simulation, and custody routes now read the same imported revision through `getSimulationDataset`. The cascade fixture remains available without being persisted. Simulations remain read-only and use the existing deterministic engine. The custody route passes the imported source records to the existing assessment service.

The import schema rejects unknown financial fields, including `dvpPairs`, because DvP relationships are not part of the shared v1 import contract. It requires UTC timestamps and source records received by the snapshot's `asOf`. It also rejects negative source amounts and quantities until the custody assessment can handle them. These are explicit validation errors rather than silently discarded data.

The local SQLite file requires a persistent writable filesystem and Node 24. Hosting on an ephemeral or read-only server filesystem requires a managed durable store before deployment. The current route has no authentication; its audit event records `actorId: "anonymous"` to indicate that the actor is unknown. Platform must add authentication and authoritative actor attribution before production use. No reconciliation mutation or correction application path is added here.

# Dataset import handoff

`POST /api/datasets/import` accepts the shared `ImportDatasetRequest`. Runtime validation covers identifiers, cross-dataset ownership, all account/instrument/source/obligation/dependency references, duplicate source identities, integer financial units, reserved inventory, and dependency cycles. Invalid bodies return `VALIDATION_FAILED` with field-level `validationIssues`; a reused dataset ID returns `REVISION_CONFLICT`. The fixed `dataset-cascade` ID is reserved for the fixture.

The repository uses Node 24's built-in SQLite driver. It creates `data/custodyos.sqlite` on the first imported-dataset access, or the path in the trusted server configuration `CUSTODYOS_DATABASE_PATH`. Fixture-only reads do not open a database. Imported datasets, institutions, accounts, instruments, source records, obligations, dependencies, balances, snapshots, and audit events are stored as relational rows. Multi-value and optional relationships use separate tables/columns; only nonfinancial metadata (`identifiers`, source `attributes`, and audit `details`) remains JSON. Each persisted row is keyed by `user_id`; during the demo phase, `CUSTODYOS_DEMO_USER_ID` supplies the single configured owner (default `demo-user`). The dataset, immutable revision `1` financial snapshot, and `DATASET_IMPORTED` audit event are committed in one SQLite transaction. SQL parameters protect dataset identifiers from injection. A second import does not replace a revision, since the v1 import request has no `expectedDatasetRevision`; future revision updates need a separate approved API contract and atomic write path.

The prototype's assets, transactions, policies, digital-twin nodes, and edges are stored in dedicated `example_*` tables with columns matching the sample objects and composite keys including `user_id`. A first-open seed copies the sample data once for the configured demo owner; `getExampleData` and `saveExampleData` read and replace only that owner's rows in a single transaction. This is demo ownership, not an authentication boundary: production requests must derive the user key from a verified session, never from caller-controlled input. Legacy imported datasets in the previous JSON-payload tables remain readable for compatibility only for `CUSTODYOS_LEGACY_USER_ID` (default `demo-user`), while new writes use the relational tables.

Demo registration uses `POST /api/users/register` with a username and SHA-256 password hash. It returns a `registrationId`, a server-generated Base32 `otpSecret`, and an expiry timestamp; the client can use the secret to display an authenticator QR code. The pending registration is held in process memory for five minutes and is not written to SQLite. `POST /api/users/register/verify` accepts the registration ID and six-digit OTP, and inserts the account into `custody_authenticate` only after successful verification. Verification is limited to five failed attempts. Pending registrations are lost on process restart and are not shared between server instances, so this implementation is for the single-process demo only. The existing login API expects the same SHA-256 password hash.

`GET /api/users/{userId}/financial-data` returns the requested owner's prototype collections (`assets`, `transactions`, `policies`, `nodes`, and `edges`) plus all relationally stored dataset records, including snapshots, source data, balances, dependencies, and audit events. A user with no stored records receives empty collections. The route intentionally has no authentication today; it trusts the path parameter and must not be exposed to untrusted users until authorization binds `userId` to a verified session.

Workspace, twin, simulation, and custody routes now read the same imported revision through `getSimulationDataset`. The cascade fixture remains available without being persisted. Simulations remain read-only and use the existing deterministic engine. The custody route passes the imported source records to the existing assessment service.

The import schema rejects unknown financial fields, including `dvpPairs`, because DvP relationships are not part of the shared v1 import contract. It requires UTC timestamps and source records received by the snapshot's `asOf`. It also rejects negative source amounts and quantities until the custody assessment can handle them. These are explicit validation errors rather than silently discarded data.

The local SQLite file requires a persistent writable filesystem and Node 24. Hosting on an ephemeral or read-only server filesystem requires a managed durable store before deployment. The current route has no authentication; the configured demo user is not an authenticated actor. Platform must add authentication and authoritative actor attribution before production use. No reconciliation mutation or correction application path is added here.
